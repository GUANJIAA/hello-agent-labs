# 第三章习题答案

## 1. 统计语言模型与N-gram

### 1.1 计算 "agent works" 在 Bigram 模型下的概率

**语料库**：`datawhale agent learns , datawhale agent works`

**词表**：`{datawhale, agent, learns, works, ,}`（逗号也算一个token）

**Unigram 计数**：
- datawhale: 2
- agent: 2
- learns: 1
- works: 1
- ,: 1
- 总词数: 7

**Bigram 计数**：
- (datawhale, agent): 2
- (agent, learns): 1
- (learns, ,): 1
- (, datawhale): 1
- (agent, works): 1

**计算 P(agent works)**：

$$P(\text{agent works}) = P(\text{agent}) \times P(\text{works} | \text{agent})$$

$$= \frac{2}{7} \times \frac{1}{2} = \frac{1}{7} \approx 0.143$$

### 1.2 马尔可夫假设与N-gram局限性

**马尔可夫假设**：
- 假设一个词的出现概率**只依赖于它前面的 N-1 个词**
- 即：$P(w_i | w_1, w_2, ..., w_{i-1}) \approx P(w_i | w_{i-N+1}, ..., w_{i-1})$

**N-gram的根本局限性**：

| 局限性 | 说明 |
|--------|------|
| **数据稀疏性** | 随着N增大，可能的组合呈指数增长，很多n-gram在训练语料中从未出现 |
| **上下文限制** | 只能捕捉局部依赖，无法建模长距离语义关系 |
| **语义理解缺失** | 基于统计共现，不理解词的实际含义 |
| **泛化能力差** | 对未见过的新词或新组合无法处理 |

### 1.3 神经网络语言模型的改进

**RNN/LSTM**：
- **如何克服**：通过隐藏状态传递信息，理论上可以捕捉长距离依赖
- **优势**：
  - 参数共享，处理变长序列
  - 能够学习词的分布式表示（词嵌入）
  - 比N-gram更好的泛化能力

**Transformer**：
- **如何克服**：自注意力机制直接建模任意位置间的依赖关系
- **优势**：
  - 完全并行计算，训练速度快
  - 真正的长距离依赖建模（不受距离限制）
  - 多头注意力捕捉不同子空间的信息
  - 可扩展性强，支持大规模预训练

## 2. Transformer架构

### 2.1 自注意力机制的核心思想

**核心思想**：**计算序列中每个位置与其他所有位置的相关性权重，根据这些权重聚合信息**

数学表达：
$$\text{Attention}(Q, K, V) = \text{softmax}\left(\frac{QK^T}{\sqrt{d_k}}\right)V$$

**直观理解**：
- 每个词生成 Query（查询）、Key（键）、Value（值）三个向量
- Query 与所有 Key 计算相似度（点积）
- 相似度经 softmax 转为注意力权重
- 用权重加权求和 Value，得到该词的上下文表示

### 2.2 并行处理与位置编码

**为什么Transformer能并行处理**：
- RNN：当前时刻的计算依赖上一时刻的隐藏状态，必须**串行**处理
- Transformer：自注意力计算只依赖输入序列，所有位置可以**同时**计算注意力权重

**位置编码的作用**：
- Transformer 本身没有位置信息（置换不变性）
- 位置编码为每个位置添加独特的位置信息
- 原始论文使用正弦/余弦函数：$PE_{(pos, 2i)} = \sin(pos / 10000^{2i/d_{model}})$
- 现代模型多使用**可学习的位置嵌入**

### 2.3 Decoder-Only vs Encoder-Decoder

| 特性 | Encoder-Decoder | Decoder-Only |
|------|-----------------|--------------|
| **结构** | 编码器+解码器 | 仅解码器（因果注意力） |
| **注意力** | 双向 + 交叉注意力 | 单向（自回归） |
| **典型模型** | BERT、T5、BART | GPT系列、LLaMA、Qwen |
| **预训练任务** | 掩码语言模型、序列到序列 | 下一个token预测 |

**为什么主流大模型采用Decoder-Only**：

1. **训练效率**：Decoder-Only 结构简单，训练更稳定高效
2. **扩展性**：更容易扩展到超大规模（数百亿参数）
3. **统一性**：生成和理解可以用同一架构完成
4. **涌现能力**：大规模自回归预训练展现出强大的涌现能力
5. **工程友好**：推理时只需维护一个缓存，部署更简单

## 3. 文本子词分词算法

### 为什么不能直接用字符或单词？

| 粒度 | 问题 |
|------|------|
| **字符级别** | 序列过长，信息密度低，难以捕捉语义 |
| **单词级别** | 词汇表过大（数百万），OOV（未登录词）问题严重，无法处理新词/拼写错误 |

### BPE解决了什么问题

**核心问题**：
1. **词汇表大小控制**：通过合并操作控制最终词汇表规模
2. **OOV问题**：任何词都可以分解为子词单元
3. **形态学信息**：自动学习词的前缀、后缀、词根等
4. **多语言支持**：统一处理不同语言的文本

**工作原理**：
- 从字符级别开始
- 迭代合并最频繁的字符对
- 最终得到平衡粒度的子词词汇表

## 4. 本地部署与实践

### 4.1 部署Qwen3-0.6B并调整采样参数

**推荐工具**：Ollama、vLLM 或 Transformers

**关键采样参数**：

| 参数 | 作用 | 调整效果 |
|------|------|----------|
| `temperature` | 控制随机性 | 低(0.1)→确定性强；高(1.0+)→创造性高 |
| `top_p` | 核采样阈值 | 低(0.1)→保守；高(0.95)→多样 |
| `top_k` | 限制候选词数量 | 小(10)→安全；大(50)→灵活 |
| `repetition_penalty` | 抑制重复 | 增大减少重复内容 |

### 4.2 提示策略对比实验

**文本分类任务示例**：

| 策略 | 示例 | 效果 |
|------|------|------|
| **Zero-shot** | "请判断这段文本的情感：{text}" | 依赖模型预训练知识，简单任务效果好 |
| **Few-shot** | 提供3-5个示例+新文本 | 通过示例引导模型理解任务格式 |
| **CoT** | "让我们一步步分析..." | 复杂推理任务显著提升准确率 |

**实验建议**：
- 选择情感分析或主题分类任务
- 准备测试集（20-50条）
- 分别用三种策略测试，对比准确率

### 4.3 闭源 vs 开源模型对比

| 维度 | 闭源模型 (GPT-4/Claude) | 开源模型 (Llama/Qwen) |
|------|------------------------|----------------------|
| **性能** | 通常更强，尤其是复杂推理 | 快速追赶，部分任务已接近 |
| **成本** | 按token付费，长期使用成本高 | 一次性硬件投入，边际成本低 |
| **可控性** | 黑盒，无法修改内部 | 完全可控，可微调/蒸馏 |
| **隐私** | 数据需上传，存在泄露风险 | 本地部署，数据完全私有 |
| **定制化** | 有限（仅API参数） | 可领域微调、量化、剪枝 |

### 4.4 企业级客服智能体选型

**推荐**：**开源大模型（如Qwen-72B、Llama-3-70B）本地部署**

**考虑因素**：

| 因素 | 说明 |
|------|------|
| **数据隐私** | 客户对话数据敏感，本地部署最安全 |
| **响应延迟** | 本地部署可控制延迟，满足实时性要求 |
| **领域适配** | 可基于企业知识库进行微调 |
| **成本控制** | 高频调用场景，自建成本更低 |
| **合规要求** | 某些行业要求数据不出境 |

## 5. 缓解模型幻觉

### 5.1 RAG（检索增强生成）

**工作原理**：
1. 将外部知识库切分为文档块，构建向量索引
2. 用户提问时，检索相关文档片段
3. 将检索结果作为上下文输入模型
4. 模型基于检索内容生成回答

**适用场景**：
- 需要最新信息的问答（新闻、股价）
- 专业领域知识（医疗、法律）
- 企业内部知识库问答

### 5.2 其他前沿方法

| 方法 | 原理 | 优势 |
|------|------|------|
| **Self-RAG** | 模型自反思，判断是否需要检索 | 动态决策，减少不必要的检索 |
| **Chain-of-Verification** | 生成后验证事实正确性 | 多轮验证提高准确性 |
| **Tool Learning** | 调用计算器、搜索引擎等工具 | 精确计算和实时信息 |
| **知识图谱增强** | 结合结构化知识库 | 关系推理更准确 |
| **多智能体验证** | 多个模型交叉验证 | 降低单一模型偏见 |

## 6. 论文辅助阅读智能体设计

### 6.1 基座模型选择

**推荐**：**长上下文模型**如 GPT-4-128K、Claude-3-200K、或 Qwen-128K

**选择因素**：

| 因素 | 重要性 | 说明 |
|------|--------|------|
| **上下文长度** | ⭐⭐⭐⭐⭐ | 论文通常很长，需要支持32K+ tokens |
| **推理能力** | ⭐⭐⭐⭐⭐ | 需要理解复杂的学术论证 |
| **多语言能力** | ⭐⭐⭐⭐ | 支持中英文论文 |
| **数学/公式理解** | ⭐⭐⭐⭐ | 理工科论文需要 |
| **成本** | ⭐⭐⭐ | 平衡性能与预算 |

### 6.2 提示词设计

```
你是一位专业的学术论文分析助手。请仔细阅读以下论文，并按以下结构进行分析：

【论文概述】
- 研究背景与动机
- 核心贡献与创新点
- 研究方法概述

【技术细节】
- 关键算法/方法详解
- 实验设计与数据集
- 主要结果与评估指标

【批判性分析】
- 论文的优点与局限
- 潜在改进方向
- 与相关工作的对比

【实用信息】
- 关键术语解释
- 重要公式说明
- 可复现性评估

请确保分析准确、客观，忠于原文，不添加原文未提及的信息。
```

### 6.3 长论文处理策略

| 策略 | 实现方式 |
|------|----------|
| **分块处理** | 按章节切分，分别总结后整合 |
| **层次化摘要** | 先段落摘要→章节摘要→全文摘要 |
| **RAG检索** | 构建论文向量索引，按需检索相关段落 |
| **滑动窗口** | 重叠窗口处理，保持上下文连贯性 |

### 6.4 确保准确性的设计

| 设计 | 实现 |
|------|------|
| **引用溯源** | 所有回答必须标注原文出处（页码/段落） |
| **不确定性标注** | 模型不确定时明确说明 |
| **原文比对** | 关键信息要求用户提供原文验证 |
| **多轮确认** | 复杂问题分步确认，避免误解 |
| **人工审核** | 重要结论建议人工二次确认 |
